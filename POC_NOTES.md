# POC Notes: Native Obsidian Rendering (Quartz vs Kiln)

> **Temporary scratch file.** Documents findings for the Quartz vs Kiln POC evaluation.
> Not part of the production Astro site. Safe to delete once a decision is made and
> recorded/acted upon.

## Goal

Evaluate whether Quartz or Kiln can natively render Obsidian markdown (wikilinks, math,
callouts, graph view) with less ongoing maintenance than the current Astro +
`scripts/obsidian-to-astro.js` conversion pipeline, while preserving the current
minimalist design and staying deployable to Netlify.

POC work happens in sibling directories outside this repo's tracked source:
- `../poc-quartz`
- `../poc-kiln`

No files under `src/`, `astro.config.mjs`, `package.json`, `scripts/`, or `netlify.toml`
in this repo are modified during this POC phase.

## Task 4: Feature Fidelity Comparison

Status: ✅ Done — verified with a real headless browser (Playwright + Chromium),
not just static HTML inspection. Playwright was not pre-installed; installed via
`npx playwright install chromium` (downloaded ~270MB of browser binaries to
`~/Library/Caches/ms-playwright`, standard local cache location, no system changes).
Both POCs were served locally (`kiln serve --port 8081`, `quartz build --serve
--port 8082`) and inspected via scripted browser checks, then servers were stopped.

| Feature | Quartz | Kiln |
|---|---|---|
| Wikilinks | ✅ Resolved to working relative link (`href="./vae-variational-auto-encoder"`) | ✅ Resolved (`href="/vae-variational-auto-encoder"`) |
| Callouts | ✅ Same class structure (`callout`, `callout-icon`, `callout-title`, `callout-content`), renders as a clean blue "Note" box | ✅ Identical class structure and near-identical visual style |
| Math ($ / $$) | ✅ **Confirmed via real browser render**: 65/65 math expressions rendered as `.katex` elements (server-side, baked into static HTML at build time). Inline math flows naturally within paragraph text. | ✅ **Confirmed via real browser render**: 65/65 math expressions rendered as `mjx-container` elements (client-side, lazy-loaded MathJax 4 — correctly triggered by `$$` block delimiters present throughout every post). Both frameworks render the same content with 0 raw/un-rendered `$$` left as plain text. ⚠️ **Visual quirk observed**: in the DDPM post screenshot, short inline expressions like `$x_0$`, `$T$`, `$i$` appear to each occupy their own line rather than flowing inline with surrounding prose, producing a choppy read for sentences with many short inline terms. Investigated the DOM: the markup is structurally correct (`<span class="math inline"><mjx-container>` sits inline right after the preceding text, computed CSS `display: inline`), so this isn't a simple display:block bug — root cause is inconclusive (possibly SVG width/overflow behavior in the reader column) and needs a deeper CSS/layout pass if Kiln is pursued further. Quartz's KaTeX output does not exhibit this in the same content. |
| Images/embeds | ✅ Copied to `attachments/`, resolves correctly. Minor artifact: literal `"\|500px"` alt text on embeds with width-but-no-caption — traced to the reconstruction script's embed syntax, not a framework bug (identical on both) | ✅ Same resolution, same artifact (confirms shared root cause in test data, not framework-specific) |
| Graph view (global) | ✅ `graph.html`/global graph component present | ✅ `graph.html`/`graph.js`/`graph.json` present |
| Graph view (local/per-post), browser-verified | ⚠️ Local graph widget renders in the sidebar but appears **very sparse** for this dataset — only 1 visible node/circle detected in the DOM on the DDPM page, and visually just a faint dot+line in the screenshot despite 3 posts + 1 wikilink existing in the vault | ✅ Local graph widget renders **richly populated** — 6 node/circle elements detected, and the screenshot clearly shows both "ddpm-denois..." and "vae-variational-auto-encoder" as labeled, connected nodes. Kiln's local graph appears to surface more of the vault structure by default for the same small dataset. |

**Resolved from earlier draft**: the initial static-HTML-only pass suggested Kiln's
math might not be rendering at all (no `katex`/`mathjax` script tags found via grep).
That was a false alarm caused by testing methodology — Kiln's MathJax loading is
purely client-side/JS-driven and invisible to static grep. Installing Playwright and
running a real headless-browser check resolved this conclusively: **both frameworks
render 100% of the math content correctly.** The real, remaining fidelity difference
is the inline-math line-flow quirk in Kiln noted above, and the local-graph density
difference — both are genuine, browser-confirmed observations, not testing artifacts.

## Task 5: Design Portability / Theming Effort

Status: ✅ Done

Reference design tokens pulled from `src/styles/new-styles.css`: background
`#fffff8` (warm off-white), text `#1a1a1a`, subtle black-alpha borders
(`rgba(0,0,0,0.08)`), system font stack (`-apple-system, BlinkMacSystemFont,
"Segoe UI", Helvetica, Arial, sans-serif`).

### Quartz

- Theming is config-driven via `quartz.config.yaml` (this is Quartz **v5** — config
  moved from the `quartz.config.ts` I originally researched for v4 to a YAML file;
  copied from the shipped `quartz.config.default.yaml` template to activate it).
- Colors are arbitrary hex values under `theme.colors.lightMode` / `darkMode` — set
  `light: "#fffff8"` directly and it took effect exactly as specified. **Confirmed via
  screenshot: the rendered background matches the production site's warm off-white
  almost exactly.**
- Font: tried setting `fontOrigin: local` with `-apple-system` as the family name to
  mirror the site's system-font stack, but this broke the build — Quartz's
  `CustomOgImages` emitter plugin unconditionally tries to fetch the configured font
  from Google Fonts for OG-image rendering regardless of `fontOrigin`, and threw an
  unhandled error when it couldn't resolve `-apple-system` as a Google Font name.
  Worked around by using **Inter** (a real Google Font, visually very close to the
  system-ui stack, and coincidentally Kiln's own default font) — build succeeded
  cleanly after that change.
- Effort: low. Editing ~10 lines of a config file gets you most of the way to a
  visual match. The OG-image font-fetch coupling is a real rough edge worth knowing
  about but has an easy workaround (pick a real Google Font instead of a system
  stack).

### Kiln

- Theming is **not** arbitrary-hex config-driven in the current release — CLI/config
  only exposes 4 fixed preset palettes (`default`, `dracula`, `catppuccin`, `nord`)
  and a fixed accent-color enum (`red, orange, yellow, green, blue, purple, cyan`).
  There is no field to set a custom background hex like `#fffff8` in `default` mode.
- Investigated the installed Go module's bundled assets
  (`~/go/pkg/mod/github.com/otaleghani/kiln@v0.9.5/assets/`): found an `old_style.css`
  containing Go template placeholders (`{{ .Theme.Light.Bg }}`) that suggest an
  **earlier** version of Kiln did support arbitrary hex theming, but the current
  `default_style.css` (the one actually used) is a fixed Tailwind-style palette with
  no equivalent template hooks — this capability appears to have been removed/
  restructured in a later release.
- Font: `font: inter` in `kiln.yaml` worked with no issues — default already closely
  resembles system-ui.
- **Confirmed via screenshot**: even with the `default` theme + light mode active,
  the background renders as stark white/light-gray, not the target warm off-white —
  a real, visible fidelity gap for this specific site's design.
- To get an exact color match in Kiln today would require either: (a) waiting for/
  requesting a feature to expose custom hex colors again, (b) post-processing the
  generated CSS output after each build (fragile, defeats "zero maintenance" goal),
  or (c) using Kiln's **Custom Mode** (its WIP full-HTML-templating system) to build
  a bespoke theme from scratch — a much larger effort, more comparable to a full
  from-scratch build than "theming."
- Effort: **high** for an exact match; **low** for "good enough" (the built-in themes
  are clean and usable, just not a precise match to this specific palette).

### Quartz — deeper customization pass (post-decision, at user's request)

After the initial config-only pass, went further to test the ceiling of Quartz's
customizability, since the user asked to get closer to an exact match:

- **Link colors**: updated `secondary`/`tertiary` in `quartz.config.yaml` to the
  site's actual link color (`rgb(68, 119, 170)`) and hover color (`#7eb3d8`) —
  cascades automatically to all internal links, sidebar, TOC, and backlinks via
  Quartz's CSS custom-property system (`var(--secondary)` etc. used throughout
  `base.scss`).
- **`custom.scss`** (a dedicated, empty override file shipped specifically for this
  purpose): added the site's 680px content max-width, heading letter-spacing,
  link hover-opacity treatment, and section-divider borders.
- **Numbered table of contents**: investigated whether Quartz's
  `@quartz-community/table-of-contents` package supports auto-numbering (like the
  site's custom `scripts/remark-toc.js`, which produces "3.1", "3.2" style labels).
  **Finding: not directly possible without deeper engineering.** The TOC plugin
  ships as a compiled npm package (only `.d.ts`/bundled `.js`, no readable source or
  exposed numbering option) — unlike the framework core, which is a full fork you
  own and can edit. Styled the existing (unnumbered) TOC to visually match
  indentation/hover color instead. A true numbered TOC would require either
  patching the compiled package's output post-build, or writing a fully custom TOC
  component from scratch (a non-trivial task, closer to a real dev task than
  "theming").
- **Mouse-trailer light effect**: this one *was* fully portable. Quartz's actual
  `<html>/<body>` shell lives in `quartz/components/renderPage.tsx`, which — unlike
  the TOC plugin — is core framework source in the forked clone, fully editable.
  Added the trailer `<div>` + a small inline pointermove script directly there,
  and ported the CSS keyframe/gradient animation into `custom.scss`.
  **Verified via Playwright**: the element renders and its animated position
  updates correctly in response to real mouse movement.
- Rebuilt and re-screenshotted (`/tmp/themed-quartz-v3-vae.png`) — sidebar, TOC, and
  backlink text now render in the correct link-blue, and the trailer's soft blue
  glow is visible near the cursor position at capture time.

**Revised takeaway on customizability**: Quartz is customizable at two very
different depths. Anything routed through its config + CSS custom-property system
(colors, fonts, spacing, borders, hover states, layout width) is trivial to change —
minutes of work. Anything that lives inside a compiled `@quartz-community/*` plugin
package (like TOC numbering) is not editable without forking that specific package's
source separately, since only the framework core ships as an editable fork by
default. Anything in the framework core itself (like the HTML shell in
`renderPage.tsx`) is fully open for edits, same as any other file in your fork.



## Task 6: Decision Summary

Status: ✅ Done

### Scorecard

| Criterion | Quartz | Kiln |
|---|---|---|
| Wikilinks | ✅ Full support, verified working | ✅ Full support, verified working |
| Callouts | ✅ Full support, verified working | ✅ Full support, verified working |
| Math ($ / $$) | ✅ Server-side KaTeX, renders inline text correctly | ✅ Client-side MathJax4, renders correctly, but ⚠️ short inline terms visually break paragraph flow onto their own lines (root cause inconclusive, needs deeper CSS investigation) |
| Graph view | ✅ Present (global + local), but local graph rendered **sparsely** for our 3-post test vault | ✅ Present (global + local), local graph rendered **richly** for the same test vault — real advantage here |
| Design portability (this site's exact palette) | ✅ Arbitrary hex config → near-exact match in minutes | ⚠️ Fixed presets only, current release; exact match needs heavier custom-mode templating |
| Setup/build complexity | Node/npm-based, fork-and-sync workflow, familiar if already using Node tooling | Single Go binary, zero Node dependency, needed installing a Go toolchain (user-local, no sudo) but the binary itself is trivial to run afterward |
| Maturity / community | High — long-established (v4→v5), large plugin ecosystem, heavily documented | Lower — young project (started 2026), small community, unsigned-binary Windows Defender flags reported (not a macOS concern), "custom mode" explicitly marked WIP in its own docs |
| Deployment (Netlify) | ✅ Documented, standard Node build | ✅ Documented (official Netlify deploy guide exists) |
| Docs accuracy | Accurate for what was tested | One inconsistency found: math docs page implies inline `$...$` triggers the lazy-load detector, but the actual `app.js` logic only checks for `$$`/`\(`/`\[` — inline-only content with zero display-math blocks would silently fail to load MathJax. Not an issue for our test posts (all had `$$` blocks), but worth knowing if adopting Kiln. |

### Recommendation

**Quartz is the safer, more complete choice for this site today.** It matched the
current design almost exactly with a small config change, renders every required
Obsidian feature correctly, and is backed by a mature, well-documented, actively
maintained ecosystem — all real reductions in the "conversion script edge-case
whack-a-mole" pain that motivated this whole investigation.

**Kiln is a legitimate, closer-to-the-metal contender and not a bad choice**, but
comes with three concrete costs to accept: (1) the inline-math line-flow visual
quirk needs a deeper fix before shipping, (2) the current release can't hit this
site's exact color palette without a much bigger "custom mode" templating effort,
and (3) it's a young, single-maintainer project — a real maintenance-risk
consideration for a personal site meant to last. Its single-binary/zero-Node-
dependency model and noticeably richer local graph view are genuine, non-trivial
advantages if those matter more than exact visual fidelity or ecosystem maturity.

**Both options fully solve the original problem** — native wikilinks, math, and
callouts, eliminating the need for `scripts/obsidian-to-astro.js` and its
accumulated edge-case patches — and both add native graph view, which the current
Astro setup has no path to at all.

### Suggested next step

Given the findings, **Quartz is the recommended pick** if the priority is
minimizing risk and matching the current design with least effort. If richer graph
view and a Node-free toolchain are more important than exact visual parity right
now, **Kiln remains viable** with the caveat that the math line-wrapping issue
should be investigated further and the color palette gap accepted (or worked around
via custom-mode) before committing.

This decision is left to you — happy to proceed with a full migration plan for
whichever framework you choose, as a separate follow-up scope (out of scope for this
POC per the original plan).
